# Security notes

Status: no external audit has been done. This file records what a self-review found and fixed, and
what is known to be weak. Treat the project as a prototype.

## Third review, 2026-10-16 (H1 to D2: git, the pack and smart HTTP endpoints, LFS, the tracker, the DHT, the helper, the host)

Method: read each new public or hostile-input surface for what an attacker who controls the hub, a publisher, a repository or a
request could do; wrote the attack as a test; fixed what worked; checked each test fails when its fix is removed
(`tests/test_review3.py`). Searched for shells, `eval`, unsafe loaders: none outside the pickle scanner. Every git command is built
from an argument list.

| Finding | Fix |
|---|---|
| **A commit rewritten away stayed fetchable by its id.** Git protocol v2 (git's default since 2.26) does not check that a wanted object is reachable, and the hub never deleted objects, so after `git push --force` to remove a leaked file, anyone could still `git fetch origin <old id>`. The same on a host. | After a branch moves to history that does not contain the old head, the hub prunes every unreachable object (`gc --prune=now`) from its repository. A test fetches the old id over protocols 0 and 2 and checks the objects are gone. **What this does not do:** the bytes of a big file the old commit pointed at stay in the blob store until the operator runs `torrenthub block`, old manifests stay as signed history, and anyone who already fetched keeps what they fetched. |
| **Anonymous readers could starve publishers.** Smart HTTP, the pack endpoint and publishing shared two git slots with no limit on waiting; two slow `upload-pack` requests (up to 4 minutes each) held every publication and pack request behind them. | Readers have their own slots (`THUB_GIT_READ_SLOTS`, 4); a request that cannot get a slot within `THUB_GIT_WAIT` (10 s) is answered 503 `Busy`. Publishing is no longer queued behind readers. |
| **The history-pack check was not bounded.** It reads a pack of up to 128 MiB into memory and ran in the thread pool with no limit, so a few signers could run many at once. | It takes a publish slot like the rest of the git work. |
| **Errors named the hub's directories.** Git's complaint (with the repository path) went back to anonymous clients from the smart HTTP and pack endpoints, to publishers from `BadGit`, and to anyone from `/api/thub/host` (which also listed the owner's repository path). | Public git errors say "git failed on the hub" and log the detail; publisher errors have the hub's paths replaced; the host's status page shows no path. |
| **A hub could put an option on the publisher's git command line.** The commit ids a hub reports for a repo went into `git cat-file -e` unchecked. | A value from a hub is used only if it is 40 hex characters (`hub_heads`, `local_has`). |
| **One address could fill a torrent's peer list in the tracker**, and nothing bounded the tracker in all. | At most 4 entries per address per torrent (`THUB_TRACKER_PER_IP`) and 1,000,000 entries in all (`THUB_TRACKER_MAX_TOTAL`). |
| **The LFS endpoint echoed what it was sent** (a client's `size` of any JSON type, up to the body limit). | Only a non-negative integer is sent back. |
| **A hub could make a client announce to an address on the client's own network.** The trackers named in a hub's torrent were used as given. | A tracker on a private, loopback or link-local address is used only if it is the hub's own address or the hub is itself on a private network (`tracker_ok`). Names are not resolved, so a name that resolves to a private address still gets through. |
| **A pointer can claim any size.** A cloned repository could say its big file is a petabyte and the client would start. | A download is refused before it starts if it cannot fit in the free space. |
| **Checked-out big files were hard links into the cache.** Editing the file in place changed the cache object that `torrenthub seed` shares. | `pull-files` copies; `seed` hashes each file and skips (with a warning) any that no longer matches its name. |
| **A race in publishing (found while testing the bound above, older than this review).** The hub answered a publication before it added the torrents to its swarm; the publisher dials at once; a dial to an unknown torrent fails and libtorrent will not retry that peer for a minute. Four publishers at once lost one every time (reproduced on the previous commit). | The torrents join the swarm before the answer, and libtorrent's retry wait is 5 s instead of 60. |

After the fixes, the full publish, clone, seed, clone-by-tracker run was repeated on the three machines with the final code: push 7.0 s, client A 7.1 s, client B (tracker only, hub peer off, web seed off) 4.8 s, nothing on the hub's HTTP counters. All three are faster than before the race fix (10.6 to 12.8 s, 10.6 s and 7.6 s).

Suspected and shown not to be a problem: a hostile pack cannot make the hub write outside its directories (the pack is indexed in a
throwaway repository, and only the pack and its index are copied, under names the hub builds from a hash it computed); the `ref` in a
manifest cannot be a path (`valid_ref`); a hub-supplied error cannot add a protocol line to the git helper (whitespace is collapsed);
the object cap, pack cap and time limit bound `index-pack`.

Known and not fixed:
- Names in a hub's torrent that resolve to a private address are not filtered by the client.
- Unicode-equivalent file names (NFC against NFD) are not treated as colliding; only case is.
- The tracker and the DHT tell the hub, and anyone running a public DHT node, which addresses ask for which infohashes.
- The client runs `git index-pack` on a hub's pack in the user's own repository, with the user's own git configuration. It is git's parser against hostile input, unreviewed.
- A tracker cannot tell an honest address from a lying one; anyone can announce from an address they control.

## Fixed in the 2026-10-16 review

| Finding | Fix |
|---|---|
| Signing in pure Python took 5.1 ms for a secret with 2 bits set and 10.1 ms for 255 set: its timing depends on the secret. The signer signs on request, so a client able to time its answers is exactly the party it must resist. | When `coincurve` is installed (`pip install 'torrenthub[fast]'`) all signing, verifying and key derivation use libsecp256k1, which is constant time and about a hundred times faster. Both backends are checked against the official BIP-340 vectors (the repo's copy is identical to bitcoin/bips master) and against each other on random, edge-case and malformed inputs. The signer reports its backend and warns when it is pure Python. The pure Python path remains the fallback. |
| A torrent received from another hub or a publisher could name any tracker or web seed, and the swarm engine would contact it. libtorrent refuses a local tracker unless its path ends in `/announce`; `http://internal-host/announce` still got a request carrying this machine's address and port. Measured, with a control. | `sanitize_torrent` keeps only the `info` dictionary, byte for byte, and adds only the operator's trackers and web seeds. It also refuses an `info` dictionary that is not in canonical form. Used for torrents fetched from hubs and for publisher torrents. |
| **The pickle scanner could not be trusted.** It read opcodes with a simplified model of the pickle machine instead of running the machine, and from reading the code I had reason to think a determined author could make it say "clean" for a file that was not. I did not build files to confirm that and did not need to. | Rewritten (`thub-scan-pickle/2`): the real unpickler runs with every import routed to one `find_class` that returns inert stand-ins and records any name off the allowlist, so the machine's own bookkeeping decides what is imported and nothing is imported or called (tested: the module a pickle names is never imported, the classes never constructed). Every pickle a loader would read is scanned: all `.pkl` entries of a zip, and up to five in a row in an older file. Refused: a zip with two entries of one name, a zip that does not start like one (loaders could read it as something else), anything unreadable, and more than 512 MiB of pickle data. Checked against real checkpoints (one legacy file and three zips from Hugging Face): all pass, no false positives. Old attestations by `thub-scan-pickle/1` should not be relied on; a replicator running the new scan will contradict a clean verdict the old one gave wrongly. |
| **Blob keys from other hubs' metadata were used to build file paths with no check.** A hash that was not hex (for example one containing `../`) made the store place blob, partial-download and torrent files outside the data directory. Verified on the path helpers; keys come from the file tables of upstream hubs, which the design treats as untrusted. | Checked three times: when metadata arrives (`files_from_info` accepts a sha256 of 64 lowercase hex digits or a git blob id of 40, a non-negative size, and a file name with no control characters, no empty, `.` or `..` parts and no leading slash), in every store path helper (`valid_key`), and at the `/blobs` and `/torrents` endpoints. Repo ids must look like `owner/name` or a bare name (`check_repo`), commit ids must be 40 hex digits, and publishing checks hashes for hex and file names for control characters. |
| File names went into the `Content-Disposition` header unencoded, so a name with a non-Latin-1 character made the download fail and a name with a quote broke the header. | An ASCII fallback name plus the RFC 5987 `filename*` form (`content_disposition`). |
| `Admission.purge()` existed but nothing called it, so quarantined events never expired in a running gateway despite the documented one-day life, and the quarantine had no overall cap. | A sweeper runs at start and every ten minutes. Strangers' events are refused with 503 when 100,000 are quarantined (`Limits.quarantine_total`); members are not affected. |
| No limit on requests per address. | A token bucket per client address on the event endpoint (burst 300, then 600 a minute) and the publish endpoint (burst 10, then 30 a minute), checked before the body is read; `THUB_EVENTS_PER_IP_BURST`, `THUB_EVENTS_PER_IP_MINUTE`, `THUB_PUBLISH_PER_IP_MINUTE` (0 turns one off). Clients that post many events (`verify-blobs`, `work`, `events-sync`) wait out a 429 using Retry-After. The address is the one uvicorn reports: behind a reverse proxy on another machine set `FORWARDED_ALLOW_IPS` to that proxy, or every client shares one bucket. |
| The event and publish endpoints read a whole request body before checking anything. A 400 MB body cost 8.3 s of CPU and hundreds of MB of memory without any credentials. | Per-endpoint body limits (`THUB_MAX_EVENT_BODY`, default 256 KiB; `THUB_PUBLISH_MAX_BODY`, default 64 MiB), enforced on the declared length and on streamed bodies. The same request is now refused in 0.33 s. Deeply nested JSON gives a clean 400. |

## Known weak, not fixed

- **Pickle files are still a risk even with the rewritten scanner** (below). Prefer safetensors. The scan says the file asks for no import outside a short tensor-rebuild list *when read by CPython's own unpickler*; a loader built on another pickle library may behave differently, and the scan says nothing about what an allowed function does with hostile arguments (for example, sizes that make a loader allocate a lot).
- The safetensors check validates structure, not content. The GGUF check is magic and version only.
- The signer protects against an agent, not against other code running as the same user, which can read the key file.
- Admission verifies a signature per event; with the Python backend that is about 20 ms. The per-address limit bounds a single address, not a distributed flood.
- A hub or relay can withhold a revocation or a newer manifest. Expiry, maximum age and asking several sources reduce this; they cannot remove it.

## Git backed publishing (added with H1)

New surface: a hub runs `git` on objects a publisher chose. The measures are in `PROTOCOL.md` section 18; the ones that matter here: every command runs in a fresh repository the hub controls, with no system or user config, no hooks and no templates, with a time limit and a file size limit; the pack is size capped; `index-pack --strict` checks the objects; the tree is refused if it holds a symlink, submodule, `.git` component, case collision or a large non-pointer file; nothing is kept until the whole publication has succeeded. What is not covered: a pack built to inflate (small on the wire, large when read) costs CPU until the time limit stops it (measured: 4.2 MB holding 4 GiB took 8.8 s to index; the limit cut it off when set lower), and only a signer the hub authorised reaches git at all; git itself (a parser of hostile input written in C) is a dependency this review did not read; and a hub that sets `THUB_PUBLISH_ALLOW_FORCE=1` lets a signer rewrite a branch it was allowed to publish.

## Hosting from your own machine (added with H2)

`torrenthub host` is a hub that listens (on every address unless `--bind` says otherwise) and holds the owner's signing key in a process that stays up. The key is read from a file and is not behind the signer process: whoever can read the file, or the process, can sign as the owner. The host serves files by link from the owner's working tree, so what it serves depends on files the owner or another program can change; a change is noticed within one poll and the file is withdrawn, but not before. It takes no uploads (publishing is off) and asks no upstream. It was not tested against a malicious consumer beyond the ordinary hub endpoints.

## Plain git (added with H3)

The client side runs `git index-pack --strict` on a pack the hub sends, in the user's own repository, and then checks that the commit is the one a manifest signed by a pinned key names and that its file table is the signed one; a hub that lies gets an error. What that does not cover: the signer must be pinned from a trustworthy source (a first clone cannot discover it); delegations are not followed; a hub can still serve an older signed manifest (freshness); a commit id is SHA-1, so the table check (sha256 of every big file and every plain file) is what carries the weight; the helper and filter read the signing key and downloaded bytes with the user's own permissions. The pack endpoint on the hub is public for served commits, rate limited per address, size capped and limited to two git processes at a time; it refuses commits that are not a served head or part of its history. Not reviewed: git's pack parser on hostile input on the client side (git is a dependency we did not read), and a deliberately slow or huge pack from a hostile hub (the client's index-pack has a 10 minute limit and no size limit beyond the disk).

## Stock git over HTTP (added with H4)

New public surface: `info/refs`, `git-upload-pack` and the LFS batch endpoint, unauthenticated and read only. `git upload-pack` runs in the hub's git sandbox with a time limit, an output size cap, no partial-clone filters and `--strict`; request bodies are size capped (4 MiB, and 4 MiB again once inflated), rate limited per address, and share two git process slots with the pack endpoint. A hosted repo is served from a copy that holds only the served branches. What stock git cannot do is verify the hub: `verify-git` exists for that and has to be run. Not reviewed: `git upload-pack` itself on hostile input; whether the per-address limit holds behind a reverse proxy (set `FORWARDED_ALLOW_IPS`, as for the other limits); the LFS endpoint under load.

## BitTorrent first for clones (added with H5)

A client now joins a swarm to fetch a file or a history pack, so it announces itself to trackers and DHT it is configured with and listens on a port; `thub.dht=false` and `thub.swarm=false` turn that off. The torrent it uses comes from the hub, so a hub chooses both the torrent and the bytes behind it; libtorrent is satisfied when they agree, which is why the whole-file sha256 is checked after, and the history pack's sha256 and infohash are in the signed manifest. The hub checks a history pack is exactly the commit's history, indexed in a repository of its own, and charges it to the signer's quota. Trackers named in a hub's torrent are used for clients only if they are `udp`, `http` or `https`; a hostile hub can still name a tracker or peer address on the client's network (the same limit as for the hub, which sanitises torrents it receives). Not reviewed: libtorrent as a downloader of hostile peers' data; what a long-lived `torrenthub seed` exposes (it listens on a port and shares exactly the files it fetched).

## The hub's tracker (added with D1)

`GET /announce` is public and unauthenticated. It answers only for torrents the hub holds and has not blocked, records the address of the connection (never a claimed `ip=`), caps peers per torrent and torrents in all, expires entries, limits announces per address and bounds `numwant`. What it cannot prevent: someone announcing many fake ports from one address, which makes that address appear many times (capped per torrent); the hub learning which addresses download which torrents; a swarm of real peers being pointed at a victim by many announcers who each can only list themselves. Behind a reverse proxy the per-address limit and the recorded address depend on `FORWARDED_ALLOW_IPS`. Not reviewed: the tracker under load; whether an attacker can use it to learn the hub's blob list by guessing infohashes (it answers differently for unknown and known ones, as a tracker must).

## The DHT (added with D2)

A client or seeder with the DHT on announces which infohashes it holds and asks for others, to every node it reaches, and listens on UDP. With `dhtpublic` on (the default) that includes the public mainline DHT, where anyone can see which infohashes a machine asks for; `thub.dhtpublic=false` (and `THUB_DHT_PUBLIC=0` on the hub) keeps a swarm private. `dht_local` switches off libtorrent's checks that refuse private and loopback nodes and node ids that do not match an address; use it only on a private network. `thub.upnp` asks the home router to open a port. Not reviewed: libtorrent's DHT against hostile nodes; what port mapping exposes.

## Dependencies

`pip-audit` (2026-10-16) found no known vulnerabilities in `lock/runtime.txt` (36 packages, everything a deployment installs) or `lock/dev.txt`. The earlier run's only findings were against `pip` 24.0 in a development environment, since upgraded.

Versions are now bounded in `pyproject.toml` (a tested floor and the next major as ceiling) and fixed exactly in `lock/`; install with `pip install -c lock/runtime.txt ...`. The full suite passes on the locked set in a clean virtualenv. Limits: the locks hold versions, not hashes, so a tampered package index is not defended against; they were built for CPython 3.12 on Linux x86_64; and a lock goes stale: re-run the audit on a schedule (`lock/README.md` has the steps). `libtorrent` is a native library with its own history of memory-safety fixes and is the dependency most worth watching.

## Not reviewed

TLS and certificate handling (the project relies on httpx and uvicorn defaults; every test and VM run used plain HTTP), the MCP server's tool surface beyond what its tests cover, the libtorrent engine and its DHT against hostile peers, git itself (`index-pack`, `upload-pack`, `pack-objects` and `gc` running on hostile input, as C code we did not read), the container and VM images used for testing, behaviour under real load (every limit was tested for being enforced, none for being the right number), and anything on Windows or macOS.

**All three reviews were done by the same author who wrote the code, by reading it and by writing attacks as tests. That finds the mistakes that author can see. It is not an independent audit, and it should not be taken for one.**
